# 游戏画面 Preview 不再依赖活动任务

状态：已接受，尚未实现；[可执行规格](../issues/preview-live-spec.md) 已发布到本地问题跟踪器。

用户已在独立 Demo 中确认连续预览的观感，并明确要求启动运行环境完成、检测到火影微端后，
任务开始前、执行与等待期间、任务结束后均能查看 Preview。
因此新版本 Preview 的可用范围由运行环境及目标游戏画面决定，不再以 Active Run 存在为前提；
它仍是只读观察能力，不决定 Run 状态、不向游戏发送输入。

该决定替代 ADR 0021 中“预览仅属于活动 Run，任务终态后不可用”的产品范围约束。
预览采用分身内现有 Worker 持有的独立只截图 Controller，经跨进程传输供主桌面 GUI 显示；
任务继续拥有自己的 Controller。该方向同时替代 ADR 0021 中仅复用任务 Controller 缓存的约束，
以增加一份采集资源换取预览与任务动作队列、生命周期的分离，避免重构已验证的任务释放流程。
传输与预览资源释放细节见规格及 [ADR 0025](0025-separate-preview-pixels-from-control-ipc.md)，
不得借此改变已验证的 Worker/Child Session 生命周期。

启动完成而匹配的游戏窗口尚未出现时，Preview 显示等待状态。窗口出现后自动显示画面；
窗口关闭后清除旧画面，低频等待并在新的匹配窗口出现时自动恢复，不要求用户手动重新连接。
这只恢复 Preview，不自动重开游戏、重跑任务或替换 Worker，不改变任务既有的失败/停止语义。
Worker 退出或 Child Session 结束仍按现有运行环境生命周期处理。

窗口仍有效但截图暂时失败时保留最后一帧，低频重试，恢复后继续更新；不新增“画面更新暂停”文字或弹窗。
该行为不覆盖窗口关闭、Worker/Session 身份失效等应清空画面的情况，也不改变任务状态。

截图方式由 MaaNOP 控制器配置决定，本仓库不为预览独立指定后端。
目标为最高约 30 fps、允许降帧且观感顺畅；继续关注资源开销，但不设 CPU/内存数值验收门槛。
GUI 预览不可见时允许停采，避免无人查看时持续工作；隐藏子桌面但仍在查看 GUI 预览不属于停采条件。

暂不增加高清采集，放大查看复用最大 640×360、保持比例的同一帧。按用户确认的游戏单窗口约束，
不设计多窗口选择。游戏最小化时遵循 MaaNOP 截图能力，不主动还原或置顶：截图失败保留上一帧，
尚无成功帧时保留占位，成功返回黑帧时直接显示，不额外识别黑屏。

取舍是接受预览独立于任务的生命周期设计成本，以满足任务前后观察游戏、等待期间连续动画的需求。
不改变 GUI/IPC 消费不得阻塞或改变 Run 的既有不变量。相关讨论见
[连续预览设计讨论](../issues/preview-live-discussion.md)。
