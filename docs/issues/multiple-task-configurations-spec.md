# 多份独立任务配置：Tab 管理与 MaaNOP Config V2

## Problem Statement

NarutoAutoGUI 当前只保存一份 MaaNOP 用户意图。用户需要为不同使用场景保留不同的任务顺序和参数，
但每次切换都必须重新编辑同一份配置，容易丢失原有选择或误用参数。

本需求是多份独立任务配置，不是同一执行计划内的同名任务实例，也不是并行执行或多运行环境。
用户需要简单的 Tab 管理；配置文件异常时，任务工作区也不应完全不可用。

## Solution

在现有任务工作区通过 Tab 切换独立配置，每份配置保留自己的任务列表、执行顺序和显式参数。
用户可以新建空配置、重命名和直接删除配置，重启后恢复上次激活的配置。

Global Option 继续显示和编辑在任务卡片中，在同一配置内共享，在不同配置间独立。
每次运行只使用当前 Active Configuration，经现有 Resolver 生成现有不可变 Run Plan。
运行期间沿用现有工作区锁，不支持运行配置 A 时浏览或编辑配置 B。

旧 V1 文件由新版 GUI 首次加载时无损包装为一份“配置 1”。
Active 指针无效时使用第一份配置；配置为空或无法正常加载时，工作区至少提供一份空的“配置 1”。
不增加恢复模式或专门的异常交互流程。异常原文件仅在后续真实修改首次替换它之前受到原始字节备份保护。

## User Stories

1. 作为用户，我希望保存多份独立任务配置，以便切换使用场景时无需重新填写参数。
2. 作为用户，我希望通过 Tab 切换配置，以便明确当前查看和编辑的是哪一份。
3. 作为用户，我希望每份配置保留自己的任务选择，以便不同场景互不干扰。
4. 作为用户，我希望每份配置保留自己的执行顺序，以便按该场景需要执行任务。
5. 作为用户，我希望不同配置可以包含同一个任务，以便为它保存不同参数。
6. 作为用户，我希望同一配置不能重复添加同一个任务，以便保持现有计划语义。
7. 作为用户，我希望每份配置的显式参数独立，以便修改 A 不改变 B。
8. 作为用户，我希望 Global Option 仍在任务卡片中编辑，以便保持已有操作习惯。
9. 作为用户，我希望同一配置中的 Global Option 在各任务卡片保持一致，以便共享参数没有多份冲突值。
10. 作为用户，我希望未显式设置的参数继续跟随当前项目默认值，以便保持现有默认解析行为。
11. 作为用户，我希望未激活分支的显式参数继续保留，以便再次启用时恢复原来的选择。
12. 作为用户，我希望新建配置完全为空，以便不会意外继承上一份配置的任务或参数。
13. 作为用户，我希望新建后立即进入新配置，以便直接开始配置。
14. 作为用户，我希望新配置获得“配置 1、配置 2……”这样的默认名称，以便无需先命名即可使用。
15. 作为用户，我希望能够重命名配置，以便使用自己熟悉的标签。
16. 作为用户，我希望允许多个配置使用相同名称，以便名称不受身份规则限制。
17. 作为用户，我希望名称不能只有空白，以便每个 Tab 都有可见名称。
18. 作为用户，我希望重命名不改变任务和参数，以便展示信息与执行内容分离。
19. 作为用户，我希望删除配置直接生效，以便不用经过额外确认或历史管理。
20. 作为用户，我希望删除只作用于指定 Tab，以便同名配置不会受到影响。
21. 作为用户，我希望删除非当前配置不切换当前 Tab，以便继续原来的操作。
22. 作为用户，我希望删除当前配置后进入左邻、没有左邻时进入右邻，以便行为可预期。
23. 作为用户，我希望最后一份配置不能删除，以便始终有可用的配置工作区。
24. 作为用户，我希望重新启动后恢复激活配置及全部配置内容，以便延续上次操作。
25. 作为用户，我希望开始任务只执行当前配置，以便不会意外串联其他 Tab 的任务。
26. 作为用户，我希望运行期间所有配置操作保持锁定，以便不会混淆当前配置和正在执行的内容。
27. 作为用户，我希望连接状态不可信时沿用现有编辑锁，以便失联不会被误判为运行结束。
28. 作为用户，我希望点击另一个 Tab 导致输入框失焦时，修改仍只属于原配置，以便参数不会串写。
29. 作为用户，我希望非法输入被拒绝并恢复已保存值，以便不需要管理草稿或手动保存。
30. 作为用户，我希望保存失败时得到现有错误提示且原文件保留，以便不会误以为操作已成功。
31. 作为用户，我希望 Tab 切换保存失败时不伪装切换成功，以便界面与实际配置一致。
32. 作为用户，我希望升级后旧任务顺序和参数原样保留，以便无需重新配置。
33. 作为用户，我希望旧配置中的显式默认值和未激活参数也保留，以便升级不改变我的意图。
34. 作为用户，我希望某份配置因项目更新而失效时仍能查看和管理它，以便修正或删除问题配置。
35. 作为用户，我希望非当前配置的执行错误不阻止其他有效配置运行，以便故障被限制在对应配置内。
36. 作为用户，我希望失效的激活指针自动指向第一份配置，以便无需理解内部标识。
37. 作为用户，我希望空配置列表自动得到一份空配置，以便仍能继续操作。
38. 作为用户，我希望无法加载配置文件时仍能使用空配置工作区，以便不会被恢复流程阻塞。
39. 作为用户，我希望仅打开异常文件不会覆盖它，以便原始数据不会因启动应用而消失。
40. 作为用户，我希望首次用新配置替换异常文件前保留原始字节，以便原始数据得到最低限度保护。
41. 作为用户，我希望异常备份失败时不覆盖原文件，以便失败不会扩大为数据损失。
42. 作为用户，我希望日常保存和删除不产生备份历史，以便配置管理保持简单。

## Implementation Decisions

### 领域模型与身份

- MaaNOP Config 是持久化容器，SchemaVersion 为 2，包含 ActiveConfigurationId 和 Configurations。
- 每个 TaskConfiguration 包含 Id、Name、SelectedTasks 和 ExplicitOptions；没有第二份全局参数存储。
- Id 是稳定、非空且唯一的配置身份；ConfigurationId 是对该 Id 的称呼，不是另一个字段。
- Name 只用于展示，trim 后不允许为空，允许重复。不得按名称查找、修改、删除或识别配置。
- Configurations 的数组顺序作为 Tab 顺序，不增加排序字段或本期未要求的 Tab 排序能力。
- 默认名称采用“配置 N”的编号形式。编号只用于展示，不承担唯一性、身份或永久序号职责。
- 新安装、空列表 fallback、异常文件 fallback 和 V1 迁移得到的首份配置均命名为“配置 1”。
- “配置 1”没有特殊身份；最后一份不能删除的规则适用于任何名称的配置。
- 每份配置拥有自己的任务集合和显式值，不共享可变参数容器。
- SelectedTasks 保存实际执行顺序，单份配置内按现有 TaskName 比较规则禁止重复；不同配置不受此限制。
- 同一配置中多个任务引用同一个 option key 时，继续共享该配置内的一个显式值。
- 配置之间独立的是用户意图；当前 PI、资源、游戏与 Worker 环境仍共享。
- 未显式设置的值继续跟随当前 PI；多配置不是项目版本或资源快照。

### 模块边界与运行

- MaaNopConfig 的持久化职责扩展为 V2 容器，以及唯一的 V1 包装迁移和有限异常文件保护。
- ProjectPlanModule 提供多配置管理，并将已选定的单份意图交给现有编辑视图和 Resolver。
- MainWindow 提供 Tab 和配置管理交互，继续沿用现有任务卡片、参数编辑器及工作区锁。
- Resolver 和显式值读取器的输入调整为单份配置；不由 Resolver 选择 ActiveConfigurationId。
- 保留默认值、显式值、Dormant Intent、嵌套激活、校验和 pipeline override 的现有解析语义。
- 每次 Start 只读取当前配置并构造一次 Run Start Attempt；不能混入其他配置的任务或参数。
- RunPlan、Protocol、Worker、PlanItemId、Runtime Profile Digest 和 Plan Digest 规则不因本需求改变。
- 配置 Id、名称和整个配置容器不进入 Run Plan 或 Worker Launch Context。
- 已提交 Run 仍由不可变 Run Plan 和 Worker Snapshot 描述；配置不是运行历史或恢复执行凭据。
- Tab 切换不得自动运行、停止任务、重启 Worker 或更换运行环境。
- 保留现有启动请求幂等语义，不能切换配置后重发另一份配置的待确认启动请求。

### 配置操作与编辑一致性

- 新建生成新 Id、空 SelectedTasks 和空 ExplicitOptions，保存后立即激活新配置，不复制现有参数。
- 删除始终按目标 Id 直接执行，无确认。删除非当前项保持 Active 不变。
- 删除当前项优先选择左邻，否则选择右邻；删除和替代 Active 的持久化构成一个完整结果。
- 最后一份配置禁止删除，正常可用的工作区始终至少包含一份配置。
- 重命名只改变 Name，不改变 Id、任务顺序和参数。
- Tab 选择、ActiveConfigurationId、任务内容、参数摘要和校验提示必须一致。
- 参数编辑事件明确属于创建控件的配置 Id，不能根据事件触发时的 ActiveConfigurationId 猜测目标。
- 点击 Tab B 引发 A 的失焦时，A 的修改只能作用于 A；旧控件的迟到事件不得修改 B。
- 参数编辑沿用“失焦、验证、保存”。非法修改不写入，恢复或重新渲染已持久化的值。
- 保存失败不覆盖原文件、不宣称成功，使用现有错误提示；该次 Tab 切换不能表现为保存成功后的切换。
- 不新增 draft、Save 按钮、dirty state 或“是否放弃修改”机制。
- 切换时不继承上一配置的拖动、展开、说明抽屉或校验状态，不持久化每个 Tab 的 UI 布局。
- Start in-flight、Starting、Running、Stopping 及现有其他不可编辑状态锁住全部配置操作。
- 锁定范围包括切换、新建、删除、重命名、任务增删、任务排序和参数编辑。
- IPC 断线、状态尚未同步等情况沿用现有编辑权限条件，不新增“运行 A、浏览或编辑 B”。

### 校验与可用性

- 分离容器结构校验和单份配置在当前 PI 下的可执行性，不将 Resolver 失败直接解释为容器损坏。
- 结构可读但任务消失、选项失效等情况保留原意图，显示该配置的现有校验错误并阻止其 Start。
- 不要求一份配置先通过 Resolver 才能被切换、查看、重命名或删除。
- 非激活配置的 PI 执行错误不阻塞其他有效配置；真正影响整个 PI 的安装或项目错误仍沿用现有处理。
- 空任务计划是可编辑的合法配置，但不能 Start。
- ActiveConfigurationId 有效时正常使用；缺失或找不到时选择 Configurations 的第一项。
- 第一项即使不可执行也仍是 fallback 目标，不擅自搜索第一份可执行配置。
- 可将修正后的 Active 指针原子写回。修正写回失败时仍提供工作区，并如实报告保存错误。
- Configurations 为空时生成一份空的“配置 1”；数组非法、Id 重复等不能当作正常容器接受。
- 配置文件无法正常读取或解析成可用容器时，GUI 至少提供一份空的“配置 1”。
- fallback 配置在其存续期间保持同一个 Id，不能每次渲染重新生成。
- 不引入未确认 Active、只读模式、recovery mode 或其他特殊产品状态。
- 工作区可用不代表不可写的磁盘也能保存成功；保存失败继续明确提示，不虚报持久化结果。
- 文件不存在与文件存在但异常分开处理，不能因简单的加载 fallback 自动覆盖已有异常文件。

### V1 到 V2 的包装迁移

- 迁移由新版 GUI 首次加载明确声明为 V1 的配置时执行；更新器继续保留配置目录，不解释配置内容。
- 必须识别源文件明确声明的 SchemaVersion，不能靠反序列化属性默认值将缺失版本猜成 V1 或 V2。
- 旧 SelectedTasks 和 ExplicitOptions 原样放入唯一 TaskConfiguration，生成 Id，命名“配置 1”并激活。
- 保留任务执行顺序、显式等于默认值的值、Dormant Intent 和结构合法的旧 option 条目。
- 不重新解释、拆分、清理 ExplicitOptions，不补写默认值或 resolved 值，不恢复成 PI 声明顺序。
- 完整读取、结构验证和 V2 构造成功后，才通过同目录临时文件、flush/close 和 atomic replace 完成迁移。
- 结构验证成功不要求在新版 PI 下可执行；语义失效在正常配置校验中报告，不阻止无损包装。
- 读取、构造或迁移保存失败时保留原 V1；工作区可用原则不授权静默覆盖尚未成功迁移的原文件。
- 后续正常加载 V2 不重复迁移，不重新生成配置 Id。
- 不提供自动降级转换或通用 migration framework。

### 异常文件首次替换保护

- 仅适用于原正式配置无法正常读取或解析，程序因此提供空配置，之后用户真实修改触发首次保存。
- 单纯启动、显示空配置或重绘不是备份及覆盖异常原文件的触发条件。
- 覆盖前先保留异常文件原始 bytes；不得为备份而解析、修复、转换或重新序列化原文件。
- 可采用相邻的 maanop-config.invalid-<timestamp>.json 命名，不覆盖已经存在的异常备份。
- 备份成功后，才按正常 atomic save 写入新 V2；备份失败则保存失败，正式原文件保持不变。
- 若备份已成功而正式保存失败，仍保持原正式文件，后续重试不需要为同一份原始内容制造备份历史。
- 后续正常保存、重命名和删除不创建此类备份；正常 Active 指针修正和 V1 迁移也不属于此场景。
- 不增加备份轮换、恢复 UI、历史列表、确认框、回收站或版本管理。

## Testing Decisions

产品行为及以下测试边界均已由用户确认。

以现有 ProjectPlanModule 公共行为为主要测试入口，复用 GUI SelfTestRunner 中创建隔离 PI 和临时配置、
编辑参数、重新打开配置并构造 Run Start Attempt 的先例。测试输入、返回视图、落盘内容和 Run Plan，
不锁定内部 helper、字段布局或调用次数，不为了本需求引入新的测试框架或 Worker 测试入口。

仅模块测试无法证明 WPF 失焦和点击顺序，因此补充真实 MainWindow 控件事件及工作区权限验证。
离屏测试能证明的范围和人工桌面验证分开记录，不把源码检查或直接调用方法描述为真实点击验收。

### ProjectPlanModule 与持久化验收

1. 新建、切换、重命名、删除和重开后，配置内容、数组顺序、Id 与 Active 指针符合约定。
2. 同名配置可共存，针对其中一个 Id 的编辑和删除不影响其他同名项；空白名称被拒绝。
3. 新建的任务和参数为空；单配置拒绝重复 TaskName，跨配置允许相同任务。
4. 两份配置选择相同任务但使用不同 global/task/nested 显式值，切换和重开后仍完全独立。
5. 同一配置的 global 在各任务编辑视图一致；显式默认值、Unset 和 Dormant Intent 保持现有语义。
6. 删除非当前项保持 Active；删除当前项选择左邻或右邻；最后一份不能删除。
7. 从不同 Active 分别生成 Run Plan，只有对应的任务、顺序及 resolved 参数，结构仍符合现有协议。
8. 当前空计划不能启动；非当前配置的 PI 错误不阻止有效配置，失效配置仍可切入和管理。
9. V1 包装保留全部意图，迁移后的 Id 在重开时稳定；新版 PI 不接受旧任务不导致迁移删除它。
10. 缺失、未知或非法版本不被属性默认值伪装成合法版本，不被误当作正常 V1 迁移。
11. 无文件、无效 Active、空列表、重复 Id、非法数组及不可解析 JSON 按各自规则保持工作区可用。
12. fallback 第一份不可执行时不自动选择其他配置；仅显示空工作区不改写异常原文件。
13. 非法参数不落盘；保存失败不损坏原文件，重开可读取原有成功保存的数据。
14. 迁移写入失败仍保留原 V1 bytes，不宣称迁移完成。
15. fallback 后首次真实修改保存前产生原始字节完全相同的异常备份，再写入可重开的 V2。
16. 备份失败不覆盖原文件；备份成功但正式保存失败也不破坏原文件。
17. 后续正常保存及删除不新增异常备份，正常迁移和 Active 修正不触发此保护。

失败路径优先使用隔离临时目录和可控的文件访问条件，通过正式模块入口观察保存结果和原文件 bytes；
不操作用户真实配置，不为注入失败建立通用文件系统抽象或恢复框架。

### MainWindow 验收

1. A 输入框仍持有焦点时点击 B，A 的合法修改只保存到 A，B 的值和参数摘要不变。
2. A 的非法输入在失焦后被拒绝并恢复已保存值，不携带到 B，不产生草稿或放弃确认。
3. 切换引发保存失败时显示现有错误，不伪装切换成功，激活 Tab 与显示内容保持一致。
4. 同名 Tab 的新建、激活、重命名、删除始终操作正确 Id，删除不出现确认框。
5. Start in-flight、Starting、Running、Stopping、断线及重新同步过程中，新操作不能绕过现有工作区锁。
6. 解锁后恢复正常编辑；任务增删、排序和参数编辑继续遵守原有权限条件。
7. 切换后错误提示、展开、拖动及说明抽屉不残留错误归属；空配置仍可正常添加任务。
8. 默认和最小支持窗口下，多个 Tab、重复名称和长名称的选择及配置管理入口可操作。
9. 至少完成一次真实运行前后切换配置的回归，确认运行中锁定、终态后恢复以及下一次使用新配置。

实现阶段运行风险相称的 GUI 构建与既有自动自检；不因配置功能修改 Worker/Protocol 的测试入口。
真实运行验证沿用既有运行链路，单独记录执行证据；未运行的交互项目不得标为通过。

## Out of Scope

- 同一配置内重复 TaskName、TaskInstanceId、per-task-instance option 或同名任务实例。
- Worker 侧配置、每个 Tab 独立 Worker、协议扩展、RunPlan 新字段或摘要规则变更。
- 同时运行多份配置、跨配置任务队列、并行、DAG、schedule 或运行期间编辑另一份配置。
- 配置复制、import/export、profiles 继承、独立 global option 页面或存储。
- 每份配置独立文件、项目根目录、运行环境或冻结的 PI/default 快照。
- draft、手动 Save、dirty state、放弃修改确认、配置删除确认或撤销。
- recovery mode、只读产品模式、备份管理、历史列表、回收站、版本管理及通用迁移框架。
- 持久化每 Tab 的展开状态、resolved options、pipeline override 或 Run 历史。
- 改造已验证的 Child Session、RDP、Task Scheduler、Session 验证与清理流程。
- 修改 MaaNOP、MFAAvalonia 或 MaaFramework；本需求不引入新的 Worker/IPC 能力。
